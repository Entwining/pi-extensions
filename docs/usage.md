# Using the extensions

## Inline skill invocation

`inline-skill-invocation.ts` completes and highlights `/skill-name` mentions inside interactive prompts. The first skill mentioned outside code is invoked through Pi's native [`/skill:name` command](https://pi.dev/docs/latest/skills#understand-how-skills-load). Other mentions are named to the model, which decides whether they request a skill. Existing leading Pi commands stay in place.

The extension replaces Pi's editor. Other extensions replacing the same component can affect its composition.

## Session footer

`session-id-footer.ts` inserts the session ID below the working directory. It retains Pi's footer statistics and extension statuses.

The extension replaces Pi's footer. Other extensions replacing the same component can affect its composition.

## Agent Guard

`agent-guard.ts` translates Pi shell, file, and search tool calls into Agent Guard events. It runs `/opt/homebrew/bin/agent-guard`. A call is blocked when the guard rejects it or cannot complete its check.

Agent Guard owns the rules and the [reason markers](https://github.com/Entwining/agent-guard/blob/main/docs/setup.md#reason-markers) in each block. This extension owns the Pi adapter. It requires Apple Silicon macOS and Agent Guard [installed through Homebrew](https://github.com/Entwining/agent-guard/blob/main/docs/setup.md#install).

Without Agent Guard, every guarded tool call is blocked. If you do not use it, [disable the extension with `pi config` or a package filter](setup.md#install).

## OS sandbox

`sandbox.ts` runs the `bash` tool and `!`/`!!` commands inside an OS sandbox built with [Sandbox Runtime](https://github.com/anthropics/sandbox-runtime) (Seatbelt, so macOS only), and blocks `write` and `edit` calls outside the same write policy. It also blocks Pi's `powershell` tool, which runs commands through an executor it cannot wrap. Pi and its extensions stay outside the sandbox.

`sandbox.ts` is on in every mode. The only way to turn it off for a session is to start Pi with `--no-sandbox`; no tool or command in the session changes it, and a single `bash` call runs outside it only [after you approve that command](#run-one-command-outside-the-sandbox). Project settings and extensions from a trusted project carry the same authority as your own: a project can filter this package's extensions or register its own `bash` tool, so the sandbox protects only sessions whose project configuration you trust. Within a session, it keeps commands from writing the paths that would change that configuration on a later start. Pi's argument parser takes the next word after an extension flag as its value, so put `--no-sandbox` before other options, not directly before the prompt. Pi turns a boolean extension flag on whenever it appears, even as `--no-sandbox=false`, so a launcher that keeps the sandbox on must leave the flag out.

The policy is read each time a session's sandbox starts (in RPC mode, twice for each new, resumed, forked, or cloned session) from `extensions/sandbox.json` in Pi's agent directory (`~/.pi/agent/extensions/sandbox.json`, or under `PI_CODING_AGENT_DIR`). An SDK host that passes another `agentDir` to `createAgentSession` still gets the policy and protections of that process-wide directory, because Pi does not tell extensions the session's own. Sandbox Runtime keeps one policy per process, so while one session in a host runs the sandbox, commands in another session of the same process are blocked, including a session that shares its resource loader or was opened from the same session file. A session releases the sandbox when it shuts down or is disposed, also while its sandbox is still starting. `--no-sandbox` applies to each session as it starts. Pi's own modes run one session at a time and finish its shutdown before the next one starts, provided an RPC client waits for one session switch to reply before sending the next; overlapping switches can leave the later sessions' commands blocked; a host that runs several sessions at once in one process meets these limits: sessions that share a resource loader use the shell settings and `--no-sandbox` value read by the latest start, two live sessions that share a session manager count as one, a session the host moves to another ID with `newSession()` keeps the sandbox after it is disposed, and a dispose without a shutdown while a sandbox starts blocks a session that starts on another loader before the stop finishes. The file holds [Sandbox Runtime settings](https://github.com/anthropics/sandbox-runtime#configuration), validated with the schema of the pinned `@anthropic-ai/sandbox-runtime` version. `network.allowedDomains`, `network.deniedDomains`, `filesystem.denyRead`, `filesystem.allowWrite`, and `filesystem.denyWrite` are required; an empty `allowedDomains` lets no domain through the proxy, while settings such as `network.allowLocalBinding` and `network.allowUnixSockets` still open local connections, and an empty `allowWrite` leaves only the paths below and Sandbox Runtime's defaults writable: `/tmp/claude`, plus `~/.npm/_logs` and `~/.claude/debug` unless `filesystem.denyRead` covers them and no `filesystem.allowRead` entry reopens them. `filesystem.disabled` is refused, because it would let commands rewrite the policy itself. Optional settings such as `network.allowUnixSockets` keep Sandbox Runtime's defaults when absent. Use absolute or `~` paths.

For each session the extension adds:

- write access to the session's working directory, after following symbolic links, and to a private temporary directory in `/tmp`, short enough for Unix socket paths inside it, which `TMPDIR` names inside commands and where commands may also bind and connect to Unix sockets;
- `NODE_USE_ENV_PROXY=1` inside commands, so that Node's `fetch` uses the proxy through which Sandbox Runtime allows network access;
- when the working directory is in a linked Git worktree, write access to the repository's Git directory, which the worktree shares with the main checkout, so commands such as `git commit` can update its refs and index; its `hooks` stay denied, and its `config` unless `filesystem.allowGitConfig` is set, as Sandbox Runtime treats a working directory's own `.git`. In either Git directory, other state that Git acts on later, such as a rebase todo, submodule Git directories, or included configuration files, is not protected;
- write denies, each as spelled and after following symbolic links, for Pi's agent directory and the project's `.pi` directory with the targets of the symbolic links directly inside them, the policy file, this package's directory, the Agent Guard program, and every directory on Pi's `PATH`;
- write denies for the `.pi` directory at the top of every writable directory (the working directory, the private temporary directory, a linked worktree's Git directory above, each `filesystem.allowWrite` entry, and Sandbox Runtime's defaults) and directly inside each of their subdirectories (`<dir>/.pi` and `<dir>/*/.pi`); when such a directory lies inside a project's `.pi`, the whole `.pi` is denied instead; and for Sandbox Runtime's built-in denies (Git hooks and config, shell startup files, editor settings) in the working directory.

Pi usually starts at those depths: in the working directory, a repository directly inside it, or a checkout directly inside a writable directory. A deeper `.pi` stays writable so commands can install and remove dependency trees whose packages ship one, such as `node_modules/<package>/.pi`. Seatbelt checks only the two paths a rename names, so a command can create a `.pi` deeper down and rename its parent into a protected depth; only the `.pi` at the top of a directory that exists when the session starts and is named without glob characters, such as the working directory, holds against that. If you start Pi anywhere but such a top, for example in a package inside a monorepo or in a checkout under a writable directory, an earlier sandboxed command could have planted the `.pi` that Pi loads there once it trusts the project, which it does without asking when `defaultProjectTrust` is `always`.

The wrapper that applies the sandbox runs in `/bin/sh`, which reads no startup files for a command, and starts Sandbox Runtime's `env` as `/usr/bin/env` rather than looking it up on `PATH`; the shell Pi is set to use, with its startup files, runs inside the sandbox.

Pi and its extensions start programs from `PATH` outside the sandbox, so commands cannot install programs there, such as with `cargo install` or `npm install -g`. A relative or empty `PATH` entry names a directory in the working directory, which then becomes read-only as well. A program whose files live in a directory that `filesystem.allowWrite` keeps writable, such as a global npm package under a writable tool directory, can still be changed by commands, so keep the programs Pi and its extensions run out of writable directories.

Extensions that Pi loads from another writable path, such as a local package inside the working directory or another project whose `.pi` is a symbolic link to a writable directory, are not protected.

`write` and `edit` run in Pi's process, so the extension checks their target, after following symbolic links, against the same allow and deny lists before the call runs, including Seatbelt's refusal to create the ancestors of a protected path. Where that check cannot reproduce Seatbelt exactly it denies. Reads by Pi's own tools are not restricted.

If the file is missing or invalid, or the sandbox cannot start, `bash`, `!` commands, `write`, and `edit` fail with the reason instead of running unsandboxed; only a `bash` call you approve to run outside the sandbox still runs. Seatbelt cannot be nested on macOS, so starting Pi from a command that already runs inside Seatbelt, such as another agent's sandboxed shell, blocks commands in the same way; `--no-sandbox` then leaves them to the outer sandbox.

### Run one command outside the sandbox

When the sandbox blocks a command the task needs, the model can call `bash` again with `unsandboxed: true` and a `justification`. Pi then asks you to confirm, showing the exact command, with any shell command prefix from your settings, its working directory, and the justification, with control and formatting characters written as escapes. Pi runs that command outside the sandbox with your full permissions only if you approve. If the command already ran inside the sandbox, that attempt may have made partial changes before it failed. Agent Guard and other `tool_call` handlers check the call before the dialog appears. Without dialogs, in print and JSON modes, the request is refused; an RPC client receives it as a `confirm` dialog. `!` commands, `write`, and `edit` have no such request, and in a session started with `--no-sandbox` the request changes nothing.

### Shadow the dialog with a judge

A judge can answer each such request alongside you, to show from its log whether it would have let the command run without asking. It changes nothing about the dialog: you still approve or decline every command, and its verdict is only recorded. To turn it on, create `extensions/sandbox-judge.json` in Pi's agent directory with `{"mode": "shadow"}`. It is read each time a session's sandbox starts; a file that cannot be read, or that holds anything else, leaves the judge off with a warning.

When the dialog opens, the judge asks the session's current model, at the session's thinking level and through the session's provider, in a request of its own. The model applies a policy adapted from [preallow](https://github.com/Entwining/mods/tree/main/plugins/preallow)'s: a command that serves your task and whose effects can be undone may run, while one that would leak information, goes beyond your task or against your instructions, or has an irreversible effect you did not explicitly ask for would come to you. It reads the messages you typed in the session since the judge was on and the commands you declined there, in the order they came, which Pi keeps as entries on the session's current branch, then the working directory, the command as it will run, and the justification. Messages from an RPC client or an extension do not count as yours. A typed message counts, in the place you typed it, once Pi delivers it as a user message on the branch: the message with the same text, or, when a skill or extension rewrote the text, the only input still waiting. Input an extension handles, a message a fork or rewind returns to the editor, and input whose delivered message cannot be told apart do not count. Pi gives each input handler the text earlier extensions returned, so an extension that loads before `sandbox.ts` and rewrites input changes what the judge reads; this package loads `sandbox.ts` before `inline-skill-invocation.ts`. Files and piped input that Pi's command line adds to the first message count as typed. Requests made while the sandbox is not running, those the dialog refuses before asking, and calls aborted before the dialog opens are not judged.

Each judged request adds one line to `sandbox-judge.jsonl` beside the config file, which sandboxed commands cannot write: the time, session ID, tool call ID, the policy's revision, the model and thinking level, any shell command prefix, the verdict and its reason, why the judge failed when it did, how long it took, and your answer: `approved`, `declined`, `aborted` when the call's abort closed the dialog, or `failed` when the dialog failed. A judgment still running when its session shuts down is logged at once with the failure `session ended`. Join the log to the session's transcript by tool call ID for the command.

Each judged request costs one more request to the session's model. In an SDK host that runs several sessions on one resource loader, Pi writes extension entries to the session that started last, so the judge's entries can land in another session. Pi records an SDK host's prompt as typed unless the host names another source. The judge's request does not pass through other extensions' `before_provider_headers` and `before_provider_request` handlers, so a route that depends on them does not apply to it.

## DeepSeek reasoning

`strip-reasoning-filler.ts` removes interjections and repeated standalone filler from replayed reasoning for DeepSeek models. It modifies the request copy and preserves the recorded transcript. The reasoning extension does nothing for other models.

The workaround depends on the provider's `reasoning_details` format. Disable or remove it when that workaround is no longer needed.
